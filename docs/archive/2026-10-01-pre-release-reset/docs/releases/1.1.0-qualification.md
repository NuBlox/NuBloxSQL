# NuBloxSQL 1.1.0 stable release qualification

This document defines the qualification contract for the single-entry `nubloxsql` package after completion of Phase 1.

## Release unit

The release unit is one npm package:

```text
nubloxsql
```

The supported public entry point is the package root. Internal SQL Core and dialect directories remain implementation boundaries shipped inside the same package.

## Stable release gates

A stable or release-candidate build must pass all of the following before publication.

### 1. Runtime and dialect verification

`npm run verify` must pass on every supported Node.js line in CI:

- Node.js 22;
- Node.js 24;
- Node.js 26.

The verification matrix includes the portable facade, SQL Core, MySQL, PostgreSQL, SQLite and SQL Server contract suites.

### 2. Live engine qualification

The existing dialect workflows must remain green for their supported live-engine matrices, including MySQL 8.4/9.7 and PostgreSQL 15/16/17/18. SQL Server qualification remains part of its dedicated workflow.

### 3. Proprietary and security boundary

The proprietary dependency and release audits must pass. The published package must retain the NuBloxSQL proprietary licence and the zero-third-party runtime package boundary.

Security CI must remain green, including protocol fuzzing and CodeQL.

### 4. Public API freeze

`docs/releases/public-api-v1.json` is the machine-readable Phase 1 public package manifest.

`npm run release:qualify` compares the root exports against that manifest. A root export cannot be added, removed or renamed accidentally. Updating the manifest is therefore an explicit public-API decision rather than an incidental implementation change.

The manifest also freezes:

- package name;
- stable version under qualification;
- JavaScript entry point;
- TypeScript entry point;
- supported Node.js range;
- canonical dialect set.

### 5. Packed npm surface

Qualification executes `npm pack --json --dry-run` and validates the actual npm file list.

Required root/runtime/declaration files must be present. Development-only trees such as `test/`, `tool/`, `.github/` and legacy `packages/` must not be published.

### 6. Clean-install JavaScript consumer

Qualification creates a temporary empty project, creates the actual npm tarball with lifecycle scripts disabled, installs that tarball locally, and executes a consumer against the installed package.

The consumer verifies:

- root `require('nubloxsql')`;
- observability schema availability;
- SQLite client creation through the root facade;
- DDL and parameterized DML;
- row retrieval;
- deep metadata introspection;
- deterministic close.

This proves the shipped tarball rather than the repository checkout.

### 7. Clean-install TypeScript consumer

The same temporary consumer compiles under TypeScript 5.9.3 with `--strict` and `--noEmit`.

The fixture verifies dialect discrimination for:

- MySQL;
- PostgreSQL and the `pg` alias;
- SQLite;
- SQL Server and the `mssql` alias;
- transaction callback dialect retention;
- capability-report dialect inference;
- transaction-policy dialect inference.

TypeScript is used only as pinned release tooling and is not added to NuBloxSQL runtime or development dependencies, preserving the zero-third-party package dependency boundary.

### 8. Publish dry run

The final `release:check` ends with `npm pack --dry-run` after all other release gates succeed.

## Command

The complete local stable release gate is:

```bash
npm run release:check
```

The qualification-only slice is:

```bash
npm run release:qualify
```

## Release decision

A build is eligible to become a stable RC only when all required CI workflows and `release:check` are green for the exact candidate commit. Publication and tagging must be performed from that qualified commit; no source changes may be introduced between qualification and publication.
