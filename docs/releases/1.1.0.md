# NuBloxSQL 1.1.0

NuBloxSQL 1.1.0 is the consolidated single-entry `nubloxsql` release line.

## Package contract

- one public npm package: `nubloxsql`;
- Node.js 22 or newer;
- proprietary licence;
- zero declared third-party npm dependencies;
- one public API routing to native dialect runtimes.

## Qualified Tier-1 dialects

- PostgreSQL 15–18;
- MySQL 8.4 and 9.7;
- SQLite through supported Node.js 22/24/26 `node:sqlite` runtimes.

SQL Server remains the supported Tier-2 native TDS runtime with dedicated protocol/type/streaming/live qualification.

## Platform surface

The release includes unified clients, tagged SQL, typed binds, prepared execution, transactions, streaming, metadata/introspection, operation controls, observability, portable errors, capability discovery and the Tier-1 SQL capability model.

The executable `capabilityOntology` separates engine support, conditional availability, lifecycle maturity and NuBlox parser/AST/validator/renderer/rewrite implementation coverage.

Released compiler scopes:

- `select-foundation-v1` — SELECT, joins, grouping, ordering and pagination;
- `select-query-v2` — CTEs, recursive CTE declarations, subqueries and derived tables;
- `select-query-v3` — UNION/INTERSECT/EXCEPT families and compound-query composition;
- `select-query-v4` — CASE, CAST, richer predicates, windows and window frames;
- `dml-v1` — INSERT, INSERT-SELECT, UPDATE, DELETE and capability-gated RETURNING;
- `dml-v2` — explicit UPSERT/conflict semantics and PostgreSQL MERGE semantic nodes;
- `dml-v3` — PostgreSQL/SQLite UPDATE FROM and PostgreSQL DELETE USING with one auxiliary table reference;
- `dml-v4` — joined and derived-table auxiliary mutation-source composition;\n- `dml-v5` — source-origin-aware bind remapping for rich mutation sources;
- `ddl-v1` — structured CREATE TABLE/INDEX/VIEW/SCHEMA/SEQUENCE and DROP TABLE/VIEW;
- `ddl-v2` — atomic ALTER TABLE add/drop/rename-column and rename-table lifecycle;
- `ddl-v3` — column type/default/nullability and named constraint lifecycle;
- `ddl-v4` — schema-object drops and statement-specific `IF EXISTS` / `IF NOT EXISTS` lifecycle semantics;
- `ddl-v5` — PostgreSQL concurrent index lifecycle and explicit DROP dependency behavior;
- `ddl-v6` — generated-expression columns plus PostgreSQL SQL-standard identity columns;
- `ddl-v7` — foreign-key action, match and deferrability semantics;
- `ddl-v8` — expression/functional index keys plus PostgreSQL INCLUDE/access-method semantics;
- `ddl-v9` — per-key ordering/collation plus PostgreSQL NULL placement/operator classes;
- `ddl-v10` — native CREATE TABLE AS query materialisation with engine-local result-schema semantics.

Wave 2 preserves source-dialect set-operation precedence. Wave 3 adds structured CASE/CAST and analytical/window nodes with target capability gating.

Wave 4 adds first-class mutation ASTs. `RETURNING` remains capability-driven: PostgreSQL is native, MySQL is rejected, and SQLite requires runtime qualification where its profile is runtime-dependent.

Wave 4b represents PostgreSQL/SQLite `ON CONFLICT`, MySQL `ON DUPLICATE KEY UPDATE`, and PostgreSQL MERGE as separate semantic families. Unsupported cross-family lowering fails closed.

Wave 6a adds PostgreSQL/SQLite `UPDATE ... FROM` and PostgreSQL `DELETE ... USING`, while keeping MySQL multi-table UPDATE/DELETE as a distinct semantic family. SQLite UPDATE FROM is runtime-version qualified from 3.33.0.

Wave 6b extends advanced DML composition with joined and derived-table auxiliary mutation sources. The query relation/join AST is reused so capabilities remain centralized. MySQL multi-table UPDATE/DELETE remains a distinct family.\n\nWave 6c adds explicit parameter-origin remapping across rich mutation sources. Parameters from SET, FROM/USING, WHERE and RETURNING are rebound through a single final binder, preserving source bindings while emitting target-dialect marker order.

Wave 5 adds structured table/column/type/constraint, index, view, schema, sequence and drop ASTs. CREATE VIEW reuses the qualified query compiler. MySQL partial-index targets fail closed and runtime-dependent SQLite capabilities require qualification.

Wave 5b adds atomic ALTER TABLE add/drop/rename-column and rename-table capabilities. SQLite `RENAME COLUMN` is modeled from 3.25.0 and `DROP COLUMN` from 3.35.0 with runtime-version evidence.

Wave 5c adds `ALTER COLUMN` type/default/nullability plus named constraint lifecycle. PostgreSQL/MySQL default lifecycle is the qualified common native subset. PostgreSQL type/nullability changes are not silently lowered to MySQL `MODIFY COLUMN`, and SQLite ddl-v3 targets fail closed rather than hiding a table rebuild.

Wave 5d adds:

- `DROP INDEX`, `DROP SCHEMA` and PostgreSQL `DROP SEQUENCE`;
- atomic `CREATE ... IF NOT EXISTS` capability states;
- atomic `DROP ... IF EXISTS` capability states;
- explicit MySQL table-scoped index identity;
- explicit separation of PostgreSQL schema namespaces from MySQL database/schema semantics.

PostgreSQL/SQLite `DROP INDEX` can be qualified by index identity alone. MySQL uses `DROP INDEX name ON table`; NuBloxSQL does not invent that table identity during cross-dialect transpilation. Likewise, same-dialect `DROP SCHEMA` is supported where native, while PostgreSQL↔MySQL schema/database translation fails closed.

The released MySQL profile rejects `CREATE INDEX IF NOT EXISTS` and `DROP INDEX IF EXISTS`; existence modifiers are therefore modeled per statement instead of as a generic dialect flag.

Wave 5e adds PostgreSQL-specific lifecycle semantics as first-class capabilities:

- `CREATE INDEX CONCURRENTLY` via `schema.concurrentIndexBuild`;
- `DROP INDEX CONCURRENTLY` via `schema.concurrentIndexDrop`;
- explicit `DROP ... CASCADE` via `syntax.dropDependency.cascade`;
- explicit `DROP ... RESTRICT` via `syntax.dropDependency.restrict`.

MySQL and SQLite observations for the ddl-v5 capabilities are unsupported rather than treated as equivalent vendor syntax. Cross-dialect lowering therefore fails closed. `DROP INDEX CONCURRENTLY ... CASCADE` is rejected, and concurrent index operations retain PostgreSQL's native requirement to run outside explicit transaction blocks.

Wave 5f adds structured generated and identity column semantics:

- `integrity.generatedColumns`;
- `integrity.generatedStored`;
- `integrity.generatedVirtual`;
- `integrity.identity`;
- `integrity.identityAlways`;
- `integrity.identityByDefault`.

The released generated-column grammar uses `GENERATED ALWAYS AS (...) STORED|VIRTUAL` with a structured expression AST. PostgreSQL and MySQL stored generated columns form the qualified common native subset. SQLite generated columns require runtime/version qualification. PostgreSQL virtual generated columns require PostgreSQL 18+ source and target evidence.

SQL-standard `GENERATED ALWAYS AS IDENTITY` and `GENERATED BY DEFAULT AS IDENTITY` are represented as PostgreSQL identity semantics. NuBloxSQL does not silently translate them to MySQL `AUTO_INCREMENT` or SQLite ROWID/AUTOINCREMENT because allocation and lifecycle semantics differ.

Wave 5g adds structured foreign-key actions, match modes, PostgreSQL deferrability/initial timing, named `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY`, runtime-qualified SQLite behavior, and fail-closed vendor differences including unsupported MySQL deferred constraints and MATCH handling.

Wave 5h adds structured expression/functional index keys, PostgreSQL `INCLUDE`, and qualified built-in PostgreSQL index access methods. PostgreSQL/SQLite expression-index semantics and MySQL functional key parts remain distinct portability families; cross-family translation fails closed.

Wave 5i adds structured per-key `ASC`/`DESC`, PostgreSQL/SQLite key-level collation identity, PostgreSQL `NULLS FIRST/LAST`, and PostgreSQL operator-class identity. Collation names are not translated across engines without an explicit semantic decision.

Wave 5j adds a first-class `CreateTableAsStatement` and native same-engine `CREATE TABLE [IF NOT EXISTS] ... AS <query>` on PostgreSQL, MySQL and SQLite. CTAS query capabilities remain visible in the plan. Cross-dialect CTAS fails closed because result-column type/affinity inference is engine-specific and has not yet been normalised.

Wave 5k adds structured PostgreSQL sequence/identity start, increment, min/max, cache and cycle options plus explicit MySQL AUTO_INCREMENT and SQLite AUTOINCREMENT semantic families. Cross-family lowering is fail-closed.

Current DDL boundaries still exclude plain SQLite ROWID aliases without AUTOINCREMENT, constrained/defaulted `ADD COLUMN`, automatic MySQL `MODIFY COLUMN` lowering, automatic SQLite rebuild migrations, multi-action ALTER TABLE, operator-class parameters/families and schema-qualified key-collation/opclass forms beyond ddl-v9, MySQL invisible/multi-valued/full-text/spatial indexes, general vendor index storage/algorithm options, sequence options, multi-object drops, concurrent reindex/cross-vendor online-index equivalence and vendor physical-storage/locking/algorithm clauses.

Compiler qualification proves grammar, AST integrity, capability planning, rendering and executable examples; it does not claim identical vendor conflict, trigger, coercion or physical-storage semantics where engines differ.

PostgreSQL COPY OUT failure handling remains hardened: output-budget and sink failures retire the affected backend connection instead of leaving an asynchronous cancellation race with later pooled work.

Metadata snapshots provide native-rich evidence plus portable metadata vocabulary v1. Tier-1 clients expose `client.diagnose(statement, options)`, retaining complete native query-plan evidence beside a deliberately small portable summary.

The release gate validates source architecture, proprietary boundaries, the public package manifest, packed-package contents, clean JavaScript/TypeScript consumer installation, Tier-1 evidence, guides and cookbook.

Dedicated packed-package gates qualify:

- `dml-v2` conflict/MERGE semantics;
- `dml-v3` auxiliary-table UPDATE/DELETE composition;
- `dml-v4` joined/derived mutation-source composition;\n- `dml-v5` rich mutation-source parameter remapping;
- `dml-v3` advanced UPDATE/DELETE composition;
- `ddl-v1` CREATE/DROP DDL;
- `ddl-v2` add/drop/rename lifecycle semantics;
- `ddl-v3` column/default/nullability/constraint lifecycle semantics;
- `ddl-v4` object-drop/existence semantics;
- `ddl-v5` PostgreSQL dependency/concurrent-index semantics;
- `ddl-v6` generated/identity column semantics;
- `ddl-v7` foreign-key action/match/deferrability semantics;
- `ddl-v8` advanced index expression/functional/covering/access-method semantics;
- `ddl-v9` index-key ordering/collation/NULL-placement/operator-class semantics;
- `ddl-v10` native CREATE TABLE AS semantics;
- `ddl-v11` identity/autoincrement/sequence-option semantics.

Live compiler qualification executes portable DDL against PostgreSQL 15–18, MySQL 8.4/9.7 and SQLite on Node 22/24/26. ddl-v5 PostgreSQL-specific semantics execute across PostgreSQL 15–18. ddl-v6 stored generated columns execute on all Tier-1 engines, PostgreSQL identity executes on PostgreSQL 15–18, and PostgreSQL virtual generation executes where the runtime qualifies PostgreSQL 18 support. ddl-v7 foreign-key semantics execute against PostgreSQL 15–18, MySQL 8.4/9.7 and runtime-qualified SQLite, with vendor-specific unsupported behavior asserted explicitly. ddl-v8 executes PostgreSQL expression/INCLUDE/access-method indexes, MySQL functional indexes, and runtime-qualified SQLite expression indexes. ddl-v9 executes per-key ordering across all Tier-1 engines, collation on PostgreSQL/SQLite, and PostgreSQL NULL placement/operator classes. ddl-v10 executes same-engine CREATE TABLE AS on PostgreSQL 15–18, MySQL 8.4/9.7 and SQLite on Node 22/24/26; cross-engine CTAS is asserted fail-closed. ddl-v11 executes PostgreSQL sequence/identity options, MySQL AUTO_INCREMENT and SQLite AUTOINCREMENT with explicit cross-family rejection.
