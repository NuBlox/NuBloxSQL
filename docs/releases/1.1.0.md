# NuBloxSQL 1.1.0

NuBloxSQL 1.1.0 is the consolidated single-entry `nubloxsql` release line.

## Package contract

- one public npm package: `nubloxsql`;
- Node.js 22 or newer;
- proprietary licence;
- zero declared third-party npm dependencies;
- one public API routing to native dialect runtimes.

## Qualified Tier-1 dialects

- PostgreSQL 15–18;
- MySQL 8.4 and 9.7;
- SQLite through the supported Node.js 22/24/26 `node:sqlite` runtimes.

SQLite qualification includes runtime/lifecycle, storage/WAL policy, maintenance, feature fidelity, diagnostics, changesets, resource governance, deterministic errors, production performance, memory behaviour, contention and corrupt-input hardening. SQL Server remains available as the supported Tier-2 native TDS runtime with dedicated protocol/type/streaming/live qualification.

## Platform surface

The release includes unified clients, tagged SQL, typed binds, prepared execution, transactions, streaming, metadata/introspection, operation controls, observability, portable errors, capability discovery and the Tier-1 SQL capability model.

The executable `capabilityOntology` separates engine support, conditional availability, lifecycle maturity and NuBlox parser/AST/validator/renderer/rewrite implementation coverage.

Released compiler scopes:

- `select-foundation-v1` — SELECT, joins, grouping, ordering and pagination;
- `select-query-v2` — ordinary/recursive CTE declarations, subqueries and derived tables;
- `select-query-v3` — UNION/INTERSECT/EXCEPT families and compound-query composition;
- `select-query-v4` — CASE, CAST, richer predicates, windows and window frames;
- `dml-v1` — INSERT, INSERT-SELECT, UPDATE, DELETE and capability-gated RETURNING;
- `dml-v2` — explicit UPSERT/conflict semantics and PostgreSQL MERGE semantic nodes;
- `ddl-v1` — structured CREATE TABLE/INDEX/VIEW/SCHEMA/SEQUENCE and DROP TABLE/VIEW;
- `ddl-v2` — atomic ALTER TABLE add/drop/rename-column and rename-table lifecycle operations.

Wave 2 preserves source-dialect set-operation precedence rather than treating compound-query text as semantically identical across engines. Wave 3 adds structured CASE/CAST and analytical/window nodes with target capability gating.

Wave 4 adds first-class mutation ASTs. `RETURNING` remains capability-driven: PostgreSQL is native, MySQL is rejected, and SQLite requires runtime qualification where its profile is runtime-dependent.

Wave 4b represents PostgreSQL/SQLite `ON CONFLICT`, MySQL `ON DUPLICATE KEY UPDATE`, and PostgreSQL MERGE as explicit semantic families rather than interchangeable syntax. The released PostgreSQL MERGE subset covers one matched UPDATE/DELETE and one not-matched INSERT ... VALUES action. Unsupported automatic cross-family lowering fails closed.

Wave 5 adds structured table/column/type/constraint, index, view, schema, sequence and drop ASTs. CREATE VIEW reuses the qualified query compiler. Capability planning covers integrity features and partial-index behavior; MySQL partial-index targets fail closed, and runtime-dependent SQLite capabilities require qualification.

Wave 5b adds a deliberately small ALTER TABLE lifecycle through atomic capability IDs:

- `schema.tableAlter.addColumn`;
- `schema.tableAlter.dropColumn`;
- `schema.tableAlter.renameColumn`;
- `schema.tableAlter.renameTable`.

This avoids treating SQLite's broad partial ALTER TABLE support as one boolean. SQLite `RENAME COLUMN` is modeled from 3.25.0 and `DROP COLUMN` from 3.35.0 with runtime-version evidence. Version qualification applies to source syntax as well as target syntax.

`ddl-v2` ADD COLUMN currently permits only a plain column name/type. Defaults, nullability constraints, keys, checks and references during ALTER are rejected because ALTER-time restrictions and existing-row effects differ across engines. ALTER COLUMN type/default/nullability, constraint lifecycle, multi-action ALTER, vendor locking/algorithm modifiers, generated/identity columns and richer physical DDL remain future scopes.

SQL type names/modifiers are structured AST data, but successful cross-dialect DDL compilation does not claim identical storage class, affinity, coercion, collation, precision or overflow behavior.

Compiler qualification proves grammar, AST integrity, capability planning, rendering and executable examples; it does not claim identical vendor conflict, trigger, row-matching or physical-storage semantics where engines differ.

PostgreSQL COPY OUT failure handling remains hardened: output-budget and sink failures retire the affected backend connection instead of leaving an asynchronous cancellation race with later pooled work.

Metadata snapshots provide native-rich evidence plus portable metadata vocabulary v1. Tier-1 clients also expose `client.diagnose(statement, options)`, which keeps complete native query-plan evidence alongside a deliberately small portable diagnostics summary.

## Release qualification

The release gate validates source architecture, proprietary boundaries, the public package manifest, packed-package contents, clean JavaScript/TypeScript consumer installation, Tier-1 evidence, guides and cookbook.

Dedicated packed-package gates qualify:

- `dml-v2` conflict/MERGE semantics;
- `ddl-v1` CREATE/DROP DDL;
- `ddl-v2` ALTER TABLE lifecycle semantics, including SQLite version gating.

Live compiler qualification executes DDL against PostgreSQL 15–18, MySQL 8.4/9.7 and SQLite on Node 22/24/26.

```bash
npm run verify
npm run test:sqlite-production
npm run release:check
```

The exact machine-readable release contracts are `public-api-v1.json` and `tier1-stable-evidence.json` in this directory.
